# Execution facade

Canonical owner for execution behavior; precedence belongs to DOCUMENT_GOVERNANCE.md. This is an intentional v0.1.1 capability extension, not unchanged extraction or application release acceptance.

## EXEC-FACADE: Public contract

One stable executable public facade is `./run.sh`. Required vocabulary: help, doctor, dev, test, lint. A simple project-owned execution-profile.json declares argv arrays, availability, mutability, prerequisites, default command and compatibility launchers; PROJECT_PROFILE.md explains local applicability and stronger protocols. No shell evaluation or policy DSL. Package, migration, screenshot-qa and full-test are optional project extensions, not required available capabilities. Agents use the applicable facade-owned project commands; ad-hoc underlying commands must not bypass its safety/observation contract. Read-only investigation and declared diagnostic fallback remain allowed when the facade is unavailable; disclose that limitation.

## EXEC-READONLY: Honest diagnostics

help is always available, returns 0 and prints vocabulary/applicability even when configuration or prerequisites are missing. doctor checks configuration, declared files/executables and supported interpreter without installing, creating files, keys or .env, starting services, applying packages or touching databases. doctor returns 0 only when all required checks pass; otherwise report PENDING / NOT CONFIGURED and exit 3. NOT APPLICABLE is informational, never evidence of a required gate passing. Status-like commands are read-only: neither runtime startup nor package application may be hidden behind them. These safety/evidence boundaries are non-waivable.

## EXEC-DISPATCH: Arguments and availability

Configured commands execute their declared argv with caller arguments forwarded literally, from repository root; no eval, implicit resolver or dependency installation. Replace the dispatcher process so signals and child exit codes are preserved. Unknown commands return 2; NOT CONFIGURED or NOT APPLICABLE execution requests return 3 with actionable output. Underlying configured-command exits take precedence over facade reservation numbers. dev may be unavailable; test must provide at least a declared minimal scaffold/base validation. lint may honestly be NOT CONFIGURED. Runtime acceptance is separate from static structure validation. The reference shell requires Bash and Python >=3.11; help has a non-mutating fallback if Python is absent.

## EXEC-MUTATION: Explicit lifecycle boundaries

Release full/delta package application, dependency installation/update, and runtime startup are distinct operations. An applicable apply-package extension must be mutating, require explicit package/version identity, validate it before changes and retain the local artifact, backup/recovery and failure-retention contract. Never infer dependency installation from release delta application. No actor-exclusive rule is imposed. Runtime must not silently install/update host packages; an explicitly declared build/start command may build container images/install locked image dependencies, disclosed in the profile. Stronger local approval, shared-data, exact-source and user-observed gates remain binding.

## EXEC-ADOPTION: Portable structure and transition

Copy the invariant dispatcher scripts/project_runner.py and canonical owner; instantiate project-owned executable run.sh, execution-profile.json and adapters. Checker validates structure only and never executes mapped commands. Profile schema 3: facade=`run.sh`; default names a command; commands map identifiers to status READY/NOT CONFIGURED/NOT APPLICABLE, mutability read-only/mutating, argv list (empty only when unavailable), prerequisites list (executable or file), and compatibility_launchers list with path/removal_boundary and the fixed runtime contract below. help/doctor are reserved read-only built-ins. Local executable paths must exist without symlink traversal; external executables are resolved only by doctor/runtime. Local compatibility launchers require an explicit removal boundary. Keep old calls during a tested transition; version-plus-status on a legacy installer remains an explicitly disclosed legacy install request, never the new status contract. Runtime/signals/argument/side-effect acceptance needs isolated tests, not a structure PASS.

Release schema 3 additionally pins executable paths for executable distribution assets; schema 3 historical snapshots keep their original tooling/schema. A complete pinned companion includes templates and runnable reference assets, while consumer adapters remain project-owned. No automatic package install, upgrade, Git commit/tag or production acceptance follows from adoption.

## EXEC-DELIVERY: Development and application delivery

Mode A is direct repository/worktree development; Mode B is external versioned full/delta APPLICATION package delivery; projects declare A, B or both for a B-to-A transition. An external environment such as Work/iWork is an optional historical example, not a mandated platform or dependency authority. Application package apply is distinct from dependency install/resolution. Delivering a changed lockfile does not prove who resolved dependencies.

Installed-project normal execution remains ./run.sh. Before installation, a separately distributable bootstrap role may use apply_package.sh: explicit full install or delta apply, identity validation, preservation and recovery under REL-ARTIFACT/REL-RECOVERY. It is not a second daily runtime launcher. A project may expose a mutating apply-package facade adapter after installation. Versioned legacy installer requests remain disclosed compatibility behavior. No fake generic applier is supplied in this release; Mode B with NOT CONFIGURED bootstrap is structurally declared but doctor PENDING and cannot claim package acceptance. READY requires a real executable project-owned/bootstrap implementation and applicable isolated acceptance evidence.

## EXEC-RUNTIME: Explicit day-zero contract

Every new project chooses native, docker or hybrid and has a real runnable development/health baseline before business logic. Docker is never inferred; native-only declares the entire Docker/container family NOT APPLICABLE and uses its configured native dev command. Docker-enabled chooses a declared Compose project/service/file, explicit host bind and host port, distinct container listen host/port, and health path or command. Hybrid configures both families. start may be mapped separately; test provides base validation and lint availability is honest.

execution-profile.json schema 3 has exact top-level keys schema_version, facade, default, commands, compatibility_launchers, runtime. Existing command records retain their schema; runtime has exact families runtime_mode, execution_facade, delivery_modes, package_apply, environment, network, docker, native, storage. The full fixed field contract is in [PROJECT_PROFILE.template.md](PROJECT_PROFILE.template.md); no policy DSL. The template JSON is a runnable native Mode A example, not unresolved placeholders. [execution-profile.docker.json](execution-profile.docker.json) is an opt-in Docker example to instantiate as execution-profile.json in a disposable/new project. Never silently replace an existing profile.

The stdlib-only reference reads explicit profile network values and optional runtime-local env overrides; process environment wins over local env, explicit CLI flags win over both. Native uses APP_BIND_HOST/APP_HOST_PORT; the container uses APP_CONTAINER_LISTEN_HOST/APP_CONTAINER_PORT; both use APP_HEALTH_PATH. Host defaults bind loopback. Port zero is an explicit disposable-test override only; declared public/listen ports are 1..65535. This reference supports explicit IPv4 addresses and no persistent storage. It exposes only health, not business capabilities.

The optional Compose reference builds python:3.11-slim with no pip/npm/resolver step, no secrets/volumes/provider services and a non-root, read-only minimal health service. The configured upstream base tag is python:3.11-slim; no image binary is distributed here. Consumers pin/review the actual image source/version/license and redistribution under DEV-LICENSE before shipping their application. Image acquisition/build remains an explicit dependency/runtime action and is never performed by doctor/checkers. Compose uses safe interpolation defaults matching .env.example; .env is optional and never copied into the build context. Real secret runtime configuration may use protected environment/secret stores instead of files.

Static validation checks schema/applicability, safe local/external paths, executable facade, mapped local files, env declarations and a bounded JSON-compatible Compose subset (JSON is valid YAML): project name, primary service, declared port mapping, healthcheck, example/default coherence and literal secret fields. Arbitrary YAML and extended Compose interpolation are not parsed by the stdlib checker; unsupported input fails with the exact limitation. Consumers may provide JSON-compatible Compose content without changing runtime semantics. Run docker compose config as a separate safe configuration gate when Docker applies. Static validation does not prove image availability, server listen behavior, health success, recovery or business acceptance. doctor also checks available executables/declared required env keys without running commands or creating .env. Missing prerequisites/evidence remain PENDING.

The v0.2.0 foundation retains these execution contracts. Read-only status/health commands probe the reference endpoint without starting it. Fixed schema-3 foundation checks delegate to canonical DEV-FOUNDATION, REL-DATA-CONTRACT, SEC-FOUNDATION and TEST-CLASSES owners; scripts/foundation_contract.py is an invariant static helper. Broad operational tooling is deferred to v0.3.0.
